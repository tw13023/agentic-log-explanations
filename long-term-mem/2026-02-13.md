### 2. Phase 2 Tested & Reverted ✅

**Tighter system prompt** — 在 SIGNATURE NAMING section 加入 bad→good examples 和 "exactly ONE `__`" 規則。

**結果**：反效果
- BGL 100-session test：13 → 15 unique sigs（更差）
- Token overhead：+189 tokens/session（~5.5%）
- 新增 signatures：`APP__LINK_SEVERED`、`KERNEL__RECEIVING_PACKET`、`APP__CREATING_NODE_MAP`
- 分析：LLM 確實讀到真實 log content（非 hallucination），但命名太 literal/verbose
- 原因：bad→good examples 讓 LLM "try to be creative" 反而偏離既有慣例

**Action**：完整 revert system prompt（在 Phase 2 test 後立即 revert）

### 3. BGL Normalizer Extended（7 New Mappings）✅

### 4. Discriminative Scores Added to Pattern Cards ✅

**Phase 3 重新定位**：discriminative scores 對 LLM 不可見（cards 只在 retrieval 中使用），因此作為 **paper metadata** 而非 LLM feature。

計算方法：keyword containment rate（anomaly sessions vs normal sessions）
- 對每個 pattern card 的 keywords，計算在 anomaly/normal sessions 中的出現比例
- `discriminative_score = anomaly_rate - normal_rate`

**BGL 結果**：34 patterns，全部 "high" discriminative（+0.48 to +0.88）
- 意味著 BGL anomalies 是 **lexical anomalies**（含有 normal session 不會出現的 keywords）

**HDFS 結果**：26 patterns，全部 "low" discriminative（≈ +0.0001）
- 意味著 HDFS anomalies 是 **structural anomalies**（keyword 相同，但 sequence/absence 不同）

每個 pattern JSON entry 新增 4 個欄位：
```json
"discriminative_score": 0.85,
"discriminative_level": "high",
"anomaly_rate": 0.87,
"normal_rate": 0.02
```

## Key Insight

**Prompt engineering 對 8B model 的 signature naming 幾乎無效。**

- Phase 1（hints）：+45 tokens → noise（14 vs 13 sigs）
- Phase 2（examples + rules）：+189 tokens → 反效果（15 vs 13 sigs）
- Normalizer（7 new mappings）：0 tokens → 29→27 sigs 改善

8B model 能正確讀取 log content（Phase 2 新 sigs 都 grounded in real logs），但無法遵守 abstract naming conventions。Post-hoc normalizer 是正確的 consolidation layer。

## Architecture Decision Record

### ADR: Prompt Engineering vs Post-Hoc Normalization for 8B Models

**Context**: Senior review suggested improving signature consistency via prompt engineering (signature hints, tighter naming rules).

**Decision**: Post-hoc normalization is the correct consolidation layer for 8B models. Prompt engineering adds token overhead without measurable benefit.

**Rationale**:
- 8B models can correctly *read* log content but cannot reliably *follow* abstract naming conventions
- Signature hints add ~45 tokens/session for zero consolidation gain
- Bad→good examples in system prompt cause the model to "try harder" but produce *more* diverse (worse) naming
- Normalizer canonical mappings are deterministic, zero-cost at inference, and trivially verifiable

**Consequences**:
- New signature variants discovered by future runs get added to normalizer, not to prompt
- Prompt engineering reserved for *structural* improvements (evidence format, output schema), not naming
