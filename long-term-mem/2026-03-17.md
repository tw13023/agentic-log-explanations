### Section 4.3 Reasoner

#### 4.3.1 LLM Configuration（v1）

The Reasoner pipeline uses GPT-5.1 as the backbone language model, accessed through the OpenAI chat-completions API with JSON mode enabled to guarantee structurally valid output. The sampling temperature is set to 0.1 to favour deterministic responses while allowing minimal variation for edge cases where a greedy decode would degenerate. Each request supplies the full system prompt (dataset context, component vocabulary, JSON schema, and evidence blocks E0 through E5) together with the user prompt containing the query session, yielding a single-turn generation with a maximum budget of 2,048 completion tokens and a 120-second timeout.

#### 4.3.2 Evaluation Metrics（v1）

Reasoner quality is measured along two complementary axes: automated verification and human judgment. On the automated side, the **Verification Pass Rate (VPR)** is the fraction of explained sessions whose outputs clear all nine verifier checks without a single failure. Because VPR is binary per session, it captures worst-case compliance; a single unsupported claim or missing signature is enough to mark the session as failed. Two additional metrics are reported: **evidence utilization**, defined as the fraction of retrieved evidence slots (E1–E5) explicitly cited by at least one claim, and **signature coverage**, the proportion of the training-derived anomaly pattern cards that appear in the full-run output. For the cost dimension, total token consumption is recorded, average tokens per session, and LLM latency at the mean and 95th percentile.

Human evaluation supplements the automated metrics on a stratified random sample of 50 sessions per dataset (100 total, seed = 42). A domain expert rates each explanation on three 5-point Likert dimensions — **correctness** (factual accuracy of the anomaly diagnosis), **completeness** (whether all anomaly signals present in the logs are covered), and **evidence grounding** (whether claims are properly supported by the cited evidence) — and assigns a binary **actionable** label indicating whether an engineer could act on the explanation without consulting raw logs. These four dimensions directly address RQ1 and provide independent validation of the automated verification pipeline.

### Section 4.5 RQ2: RAG Ablation

#### 4.5.1 Ablation Design (v1)

RQ2 asks whether retrieval-augmented generation (RAG) materially improves the evidence grounding of explanations, or whether the LLM can produce adequately grounded explanations from the query session alone. This question is evaluated through three complementary analyses.

**Metrics.** Two metrics are adopted from the RAGAS framework [XX] and adapted to the evidence-slot setting of this work, alongside a third metric specific to evidence-grounded explanation:

- *Faithfulness*: the fraction of claims whose cited evidence identifiers exist in the evidence mapping and contain relevant content. A claim is faithful if it cites at least one valid evidence slot (E0–E5). This serves as a control metric: the combination of JSON-mode generation, evidence-labelled prompts, and low sampling temperature produces consistently valid citations in a single pass, so Faithfulness is expected to be 1.0 regardless of retrieval condition.

- *Context Precision@K* (K = 4): a rank-aware retrieval quality metric. For each retrieved evidence slot E1–E4, a binary relevance judgment v_k indicates whether the slot was cited by any claim. Context Precision@K is then:

  Context Precision@K = sum(Precision@k * v_k) / sum(v_k)

  where Precision@k = sum(v_j for j=1..k) / k. Higher values indicate that the retriever ranks relevant evidence earlier.

- *Grounding Breadth*: the fraction of claims citing at least one external evidence slot (E1–E5) rather than only the query session (E0). This is the discriminating metric for RQ2: it measures the extent to which RAG enables the LLM to cross-reference its analysis against known anomaly patterns from the evidence store.

**Conditions.** The ablation compares two conditions. In the *RAG-on* condition, the full pipeline supplies E0 (query session), E1–E4 (BM25-retrieved anomaly sessions), and E5 (normal contrast session) in the prompt. In the *no-RAG* condition, only E0 is provided: the retrieval step is bypassed and the prompt contains only the query session. Both conditions use the same LLM configuration (Section 4.3.1), prompt template, and verification loop. The ablation is applied to a stratified sample covering all unique anomaly signatures — 388 sessions (237 signatures) for BGL and 245 sessions (98 signatures) for HDFS.

**Corpus scope validation.** A supplementary analysis compares retrieval results when the BM25 corpus is restricted to training data (the production setting) versus expanded to the whole dataset. For 100 randomly sampled anomaly sessions per dataset, the top-4 retrieved evidence is compared under both corpus scopes. An overlap rate exceeding 85% validates that the train-only corpus provides sufficient coverage, confirming that the pipeline does not require access to test data for effective retrieval.

**Baseline metrics (RAG-on).** Table A reports the RAGAS-style metrics computed on the full RAG-on pipeline output. Although the verifier's keyword-match check still passes — because E0 contains sufficient lexical overlap with the claim — the structural invalidity of these citations demonstrates that the LLM attempts to cross-reference even when no external evidence is provided. The absence of retrieved evidence does not suppress the cross-referencing behavior; it merely makes it hallucinatory.

### Section 4.6 RQ3: Cost-Quality Trade-off under Gating

#### 4.6.1 Gating Strategy Comparison (v1)

RQ3 investigates whether budget-constrained gating (selecting a subset of Screener-flagged anomalies for full LLM explanation) can reduce cost while preserving coverage of the anomaly signature catalogue. Given N anomalous sessions, the gating module selects K = floor(B * N) sessions for explanation, where B in (0, 1] is the budget ratio. Four deployable strategies (using only pre-LLM information) and one privileged reference strategy are evaluated:

- **Random**: uniform random sampling without replacement.
- **Uncertainty**: top-K by u(x) = 1 - margin(x), where margin is the Screener's softmax margin between the two most probable classes. Higher u(x) indicates lower Screener confidence and, hypothetically, greater information gain from a full LLM explanation.
- **Novelty**: top-K by n(x) = 1 - bm25_max(x) / max(bm25_max), where bm25_max is the highest BM25 similarity against the evidence store. Sessions with low similarity to previously stored explanations are assumed to represent novel fault types.
- **Combined**: top-K by s(x) = alpha * u(x) + (1 - alpha) * n(x), mixing uncertainty and novelty with tunable weight alpha.
- **Upper Bound** (privileged): greedy selection of one session per signature, rarest first, until the budget K is exhausted. This strategy is non-deployable because it requires knowledge of anomaly signatures, which are only available after LLM execution. The Upper Bound achieves 100% coverage at every tested budget level because the minimum budget K = floor(0.10 * N) exceeds the number of unique signatures on both datasets (237 for BGL, 98 for HDFS).

The primary evaluation metric is **Signature Coverage**: the fraction of unique anomaly signatures in the full corpus that are represented among the selected K sessions.

**Quality invariance.** Across all strategies and all budget levels on both datasets, every selected session achieves a Verification Pass Rate of 1.0. This budget-invariant quality result means that gating is purely a coverage-versus-cost decision: the quality of each individual explanation is unaffected by the selection criterion.

**Strategy ranking.** Table C presents signature coverage across strategies at three operationally relevant budget levels. Uncertainty gating dominates all other deployable strategies at B <= 0.50 on both datasets. At B = 0.10, Uncertainty achieves 49.8% coverage on BGL and 55.1% on HDFS, surpassing Random by 22.5 and 13.5 percentage points respectively. At B = 0.20, the advantage widens to 25.4 pp (BGL) and 18.9 pp (HDFS). Figure C visualizes the full coverage-cost Pareto curves for all strategies.

**Novelty failure.** The Novelty strategy performs poorly on BGL and catastrophically on HDFS, where it achieves only 3.1% coverage at B = 0.10 (versus Uncertainty's 55.1%). The root cause is low discriminative power in the novelty signal: the coefficient of variation (CV) of n(x) is only 0.29 on BGL and 0.26 on HDFS, indicating that nearly all sessions receive similar novelty scores. By contrast, the uncertainty signal u(x) exhibits CV values of 51.84 (BGL) and 43.79 (HDFS), two orders of magnitude greater spread, providing a far more effective basis for session prioritization. The Combined strategy inherits this weakness. Because the mean of u(x) is orders of magnitude smaller than that of n(x) in absolute terms (BGL: mean u(x) = 0.0001, mean n(x) = 0.61; HDFS: mean u(x) = 0.0004, mean n(x) = 0.72), a weighted combination at the default alpha = 0.5 is dominated by the novelty term. Combined coverage consequently tracks Novelty at every budget level (e.g., 33.8% vs. 33.3% at B = 0.10 on BGL), and the optimal mixing weight is alpha = 1.0 (Section 4.6.2), at which point Combined reduces to pure Uncertainty.

#### 4.6.2 Budget Sensitivity Analysis (v2 — compact, insight-driven)

Sweeping the mixing weight alpha from 0.0 to 1.0 across three budget levels confirms that the optimal weight is alpha = 1.0 on both datasets — pure uncertainty with zero novelty contribution. Adding any novelty weight monotonically degrades coverage, corroborating the CV analysis in Section 4.6.1. The production gating module accordingly uses u(x) = 1 - margin as the sole selection criterion.

At B = 0.20, Uncertainty gating covers 66.2% (BGL) and 73.5% (HDFS) of all anomaly signatures while reducing LLM token consumption by 79.6% and 75.4%, respectively. Increasing the budget to B = 0.50 reveals a dataset-dependent trade-off: on BGL, coverage rises by only 6.8 pp (to 73.0%), a clear plateau driven by the large signature space (237 types), while on HDFS, coverage jumps by 20.4 pp to 93.9%, approaching completeness thanks to its smaller signature space (98 types). The optimal operating point therefore depends on domain requirements: B = 0.20 offers the best cost-coverage ratio when broad but incomplete coverage suffices, whereas B = 0.50 is preferable when near-complete signature coverage is required and the signature space is compact.

### Section 4.7 Discussion (v1)

The three research questions reveal a layered structure in which each finding enables the next. The 100% verification pass rate established in RQ1 is not merely an encouraging quality metric; it is a prerequisite for the gating analysis in RQ3. Because every individual explanation passes all nine checks regardless of which sessions are selected, the selection problem reduces to maximising signature coverage under a token budget, with no quality trade-off to model. This "generate once, verify always" property arises from the interaction of three design choices: JSON-mode structured output, evidence-labelled prompts, and low sampling temperature (0.1). Together these constraints produce valid, citation-backed explanations in a single LLM call, eliminating the need for rejection sampling or iterative re-generation loops.

RQ2 demonstrates that retrieval-augmented generation is structurally necessary rather than merely beneficial. Without retrieved evidence, the LLM does not simply produce less grounded explanations; it fabricates evidence identifiers that do not exist in the prompt (100% hallucination rate for E5 across both datasets). This finding suggests that the cross-referencing behaviour encoded in the prompt template's three-claim structure is inherent to the generation process: the model attempts to cite external evidence whether or not such evidence is available. RAG channels this behaviour onto real, verifiable evidence slots, converting a liability (hallucinated citations) into a strength (grounded cross-references). The practical implication is clear: any deployment that omits the retrieval stage risks producing explanations that appear well-structured but contain fabricated supporting evidence, a failure mode that the verifier's keyword-match check alone cannot reliably detect.

The gating analysis in RQ3 yields a actionable but dataset-dependent deployment recommendation. Uncertainty gating (u(x) = 1 - margin) outperforms all other deployable strategies, driven by the two-order-of-magnitude advantage in discriminative spread (CV of 51.84 vs. 0.29 on BGL). The failure of the novelty signal (n(x) based on BM25 similarity) deserves attention: its near-zero coefficient of variation means that almost all sessions receive similar scores, rendering top-K selection essentially random. One possible explanation is that BM25 similarity against the evidence store captures lexical overlap with known patterns, but log sessions within the same system tend to share boilerplate phrasing, compressing the score distribution. The optimal operating point depends on the signature space: compact spaces (HDFS, 98 types) benefit from budgets up to B = 0.50, while large signature spaces (BGL, 237 types) plateau at B = 0.20. In both cases, the token savings (75-80%) substantially exceed the coverage loss, making uncertainty gating viable for production cost control.

Several limitations should be noted. First, the framework is evaluated with a single LLM backbone (GPT-5.1); generalisation to smaller or open-source models remains untested. Second, the two public datasets (BGL and HDFS) represent high-performance computing and distributed storage workloads, respectively, but do not cover microservice, network, or security log domains. Third, human evaluation relies on a single domain expert rating 50 sessions per dataset; inter-rater agreement cannot be assessed. Fourth, the anomaly signature taxonomy is generated by the LLM itself, with no external gold standard for validation. While manual inspection confirms that singletons represent genuine rare failures (Section 4.4.3), a systematic evaluation of signature quality would strengthen this claim. Fifth, the evidence store is static throughout evaluation; temporal drift in log patterns could degrade retrieval quality over time, an effect not measured in this work. Finally, the gating simulation operates post-hoc on pre-computed explanations rather than in a live deployment setting.

### Section 5 Conclusion (v1)

This work presents Screener-Reasoner, a two-stage framework for log-based anomaly detection and explanation. The Screener stage employs a Linformer encoder with GPT-4 BPE tokenization to classify log sessions at linear complexity, eliminating the need for a heuristic log parser and resolving the out-of-vocabulary problem that limits template-based approaches. The Reasoner stage extends detection into explanation: for each flagged anomaly, a retrieval-augmented LLM generates a structured, evidence-grounded explanation comprising three claims (observation, pattern-match, and contrast), each citing specific evidence slots drawn from the query session and from BM25-retrieved reference sessions. A nine-check automated verifier enforces structural and factual constraints in a single pass, and a signature normalizer aggregates explanations into a taxonomy of anomaly types.

Experiments on the BGL and HDFS public log datasets yield several findings. The Screener achieves state-of-the-art detection accuracy without log parsing or input truncation, preserving all contextual information in arbitrarily long sessions. The Reasoner produces explanations that pass all verification checks (VPR = 1.0) on both datasets, with human evaluation confirming near-perfect correctness (4.94/4.92) and 100% actionability. RAG proves structurally necessary: without retrieved evidence, the LLM hallucinates evidence identifiers in 100% of sessions, whereas RAG grounds two-thirds of all claims against external evidence (Grounding Breadth = 0.667). For cost control, uncertainty-based gating (u(x) = 1 - margin) covers 66-74% of the anomaly signature catalogue at only 20% of the LLM budget, with the optimal operating point depending on the size of the signature space.

Several directions remain open. Evaluating the framework with smaller or open-source LLM backends would clarify whether the single-pass verification property generalises beyond GPT-5.1. Extending the evidence store with online update mechanisms would address temporal drift in log patterns, which the current static design does not handle. Replacing or augmenting BM25 with dense or hybrid retrievers may improve retrieval quality for log domains where lexical overlap is less informative. Validating the gating strategy in a streaming deployment, where sessions arrive in real time, would bridge the gap between the post-hoc simulation reported here and operational use. Finally, developing a byte-level tokenization method that segments log messages without splitting parameters and technical terms (such as IP addresses or memory addresses) into sub-words would reduce input sequence length and better preserve the contextual features of system logs.
