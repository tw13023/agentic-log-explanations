## Late Addition (2026-02-15): Singleton Investigation + Verification Corrections

### DATANODE__BLOCK_VERIFICATION_SUCCEEDED (1 session)

Investigated the SME-flagged suspicious singleton `DATANODE__BLOCK_VERIFICATION_SUCCEEDED` for session `HDFS_blk_-1478843903114016209`.

**Finding: `max_log_lines=20` truncation artifact.**

The session has 30 lines. The LLM only saw L1-L20 (all normal INFO messages). The actual anomaly is at L27: `WARN dfs.FSDataset: Unexpected error trying to delete block. BlockInfo not found in volumeMap.` — this was never shown to the LLM.

The most distinctive event in the visible L1-L20 was L14: `Verification succeeded for blk_-1478843903114016209`, which the LLM used to name the signature. Additionally:
- The `explanation.summary` says "BLOCK_VERIFICATION_**FAILED**" (LLM defaulted to the dominant pattern name)
- The `signature.name` says "BLOCK_VERIFICATION_**SUCCEEDED**" (LLM used the literal log text)
- The pattern_match claim fabricates evidence matches at E1-L14 and E2-L14 (actual content: block transfer/replication, not verification)

**Impact:** 1/2,527 sessions (0.04%) — negligible. No normalizer change made.

**Systemic implication:** `max_log_lines=20` can hide anomaly signals that appear late in long sessions. This case is the only instance in HDFS where it caused a visible problem.

### Verification Failure Analysis Corrected

Original analysis stated E5 "does not exist" — this was wrong. The pipeline retrieves 6 evidence documents per session: E0 (query) + E1-E4 (anomaly) + E5 (normal). The `evidence_id_mapping` for both failed sessions confirms E5 is present and valid. The actual failure: the LLM wrote bare `E5` as a span instead of `E5-L{n}` format. The verifier's `_parse_span()` requires `-L` in every span string.

Updated `HDFS_full_run_summary_20260214_231017.md` with corrected analysis.

## Architecture Decision Record

### ADR: Verification Layer as Hallucination Detector

**Context**: BGL full run produced 2 verification failures out of 6,290 explained sessions. Investigation revealed both are LLM hallucinations.

**Finding**: The verification layer (evidence coverage check) effectively functions as a **hallucination detector** — not just a structural validator. When the LLM generates claims about patterns not present in the evidence store, evidence coverage drops to 0%, triggering a failure.

**Implication**: The 99.97% verification pass rate has dual meaning:
1. **Structural reliability** — 99.97% of LLM outputs conform to expected JSON schema and reference valid evidence
2. **Grounding quality** — sessions with verification failures are candidates for LLM hallucination, providing a lightweight proxy for factual accuracy

**Limitation**: This only catches hallucinations where the LLM fabricates patterns absent from the evidence. It cannot catch cases where the LLM references real evidence but draws incorrect conclusions.
