### 1. HDFS Verification Failure 根因分析 ✅

**背景：** 昨日 HDFS GPT-5.1 full run 中有 4 筆 session 的 `cited_severity` check（Check 9）失敗，理論上這些 session 應由 structural anomaly bypass 保護。

**4 個 failing sessions：**

| Session ID | 簡短描述 |
|-----------|---------|
| `HDFS_blk_7334665610194699862` | `NAMENODE__BLOCK_INVALIDATION_AFTER_RECENT_REPLICATION` |
| `HDFS_blk_4457957945336968750` | `NAMENODE__EXCESS_REPLICATION_DELETION` |
| `HDFS_blk_3731756724515693342` | `NAMENODE__BLOCK_IMMEDIATE_INVALIDATION` |
| `HDFS_blk_6581521916630120356` | `NAMENODE__BLOCK_IMMEDIATELY_INVALIDATED` |

**調查路徑：**

1. 確認 4 筆全都失敗在 Check 9（`cited_severity`），error message：`"0/N cited E0 lines contain error/warning keywords — likely hallucination"`
2. 檢查 bypass 邏輯（`src/verifier.py` line 666-683）：bypass 條件為「session 完全沒有 severity keyword」
3. 從 `logs/HDFS.log` grep 出 4 筆 session 的原始行，逐行比對 `SEVERITY_KEYWORDS`
4. **發現：** 每個 session 含 3 行 `INFO dfs.DataNode$BlockReceiver: Receiving empty packet for block blk_XXX`
5. `'Receiving empty packet'` 在 `SEVERITY_KEYWORDS` 中 → `session_has_any_severity = True` → bypass 不觸發
6. GPT-5.1 正確以「序列結構（空包接收 → 多副本 → 立即刪除）」為解釋核心，引用流程開始/結尾的行，不引用 `Receiving empty packet` 那幾行
7. Cited lines = 全部 INFO 且不含任何 keyword → `cited_severity` FAIL

**根本矛盾：**
`cited_severity` check 假設「keyword = cited evidence」，但 pattern-based anomaly 的 evidence 是**序列結構**，而非某一關鍵字。bypass 本應保護這類 session，但舊條件（完全無 keyword）比實際需求更嚴格。

### 2. Verifier Fix：Non-INFO Severity Bypass ✅

**修改檔案：** `src/verifier.py`（`_check_cited_severity` method，lines 666-692）

**舊邏輯：**
```python
session_has_any_severity = any(
    any(kw in line for kw in self.SEVERITY_KEYWORDS)
    for line in e0_lines
)
if not session_has_any_severity:
    # bypass → PASS
```

**新邏輯：**
```python
severity_lines = [
    line for line in e0_lines
    if any(kw in line for kw in self.SEVERITY_KEYWORDS)
]
non_info_severity_lines = [
    line for line in severity_lines
    if " INFO " not in line
]
session_has_real_severity = bool(non_info_severity_lines)
if not session_has_real_severity:
    # bypass → PASS
```

**設計原則：** bypass 的判斷基準應是「有沒有真正的 WARN/ERROR 行」，而非「有沒有任何包含 severity keyword 的行」。`Receiving empty packet` 等 keyword 出現在 INFO 行，屬結構性訊號，不應阻止 bypass。

**Backward compatibility 分析：**

| session 狀況 | 舊邏輯 | 新邏輯 |
|---|---|---|
| 完全無 severity keyword | bypass → PASS | 同樣 bypass → PASS ✅ |
| keyword 全在 INFO 行 | 未 bypass → FAIL ❌ | bypass → PASS ✅（4 個修正） |
| 有真正的 WARN/ERROR 行 | 未 bypass → cited check | 同樣未 bypass → cited check ✅ |

→ **Zero regression**。舊邏輯下能 bypass 者在新邏輯下仍能 bypass；舊邏輯下進入 cited check 且 PASS 者邏輯不變。

**驗證結果：** 4 個 failing session 在新邏輯下：
- `non_info_severity_lines = 0`（所有 keyword 行都是 INFO）
- bypass 觸發 → PASS ✅

**Commit：** `a3cddcb` — `fix: cited_severity bypass now checks non-INFO severity lines`

## Technical Notes

### `Receiving empty packet` 的語義
HDFS DataNode 在完成 block transfer 時會發送 empty packet 作為 end-of-block 信號。這些 `Receiving empty packet` 的 INFO 行是正常 block lifecycle 的一部分，但因出現在「excess replication → immediate deletion」的 session 中，使 verifier 誤判為需要 keyword 引用的嚴重性事件。

### 修正的更廣泛意義
`SEVERITY_KEYWORDS` 是一個混合清單，同時包含：
1. **Level keywords**（`WARN`, `ERROR`, `FATAL`）— 真正的嚴重性指標
2. **Content keywords**（`Receiving empty packet`, `Redundant addStoredBlock`）— HDFS 特定的行為模式

舊的 bypass 邏輯把兩類一視同仁。新邏輯透過檢查 log level（`' INFO ' not in line`）來區分：content keyword 出現在 INFO 行中屬結構性描述，不算 real severity。

**Root cause diagnosis:**

The STRUCTURAL tag is appended as a single final line to each normalized evidence document. It encodes *operational outcomes* (exception counts, lifecycle classification) but does not enumerate which log operation types are present in the body lines. When generating cross-evidence contrast claims (Claim 3), the model treated a "normal outcome" label (e.g., `exceptions=0`, `NORMAL_FLOW`) as proof that certain log operations were absent from the reference session, whereas those operations were actually present — they simply completed without error.

This is a **structural tag semantic granularity mismatch**: the tag operates at outcome level, but Claim 3 requires operation-level verification.

**Paper description (accepted, Version B):**

> Evidence grounding scores (mean = 4.04) were slightly lower than correctness and completeness (both 4.99). The gap arises because each reference evidence document carries a compact outcome label (e.g., `exceptions=0`, `NORMAL_FLOW`) but does not enumerate which log operations occurred. The model occasionally treated a "normal outcome" label as proof that certain operations were absent from the reference session, whereas those operations were actually present — they simply completed without error. This led to contrast claims that were directionally correct but overstated at the event level.
