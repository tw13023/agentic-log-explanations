### 草稿正文（v3 — code-verified）

The Prompt Builder assembles the query session and the retrieved evidence into a two-part prompt from which the LLM generates a structured, machine-verifiable explanation. Let $E_0$ denote the query session, $\{E_1, \ldots, E_5\}$ the retrieved evidence, $\hat{p}$ the anomaly probability, and $m$ the confidence margin produced by the Screener. The prompt $P$ is constructed as:

$$P = (P_{\text{sys}},\ P_{\text{usr}})$$

$$P_{\text{sys}} = \text{Template}(\mathcal{D},\ \mathcal{S})$$

$$P_{\text{usr}} = \text{Format}(E_0,\ \{E_1, \ldots, E_5\},\ \hat{p},\ m)$$

where $\mathcal{D}$ is the dataset configuration and $\mathcal{S}$ is the output specification defined below. The system prompt $P_{\text{sys}}$ defines the analytical context: dataset identity, component vocabulary (e.g., KERNEL and APP for BGL; DATANODE and NAMENODE for HDFS), the $E_i$-$L_j$ span notation introduced in Section 3.2.2, the three required claim types (observation, pattern\_match, and contrast), the signature naming convention, and an annotated output example that specifies expected fields and constraints. The user prompt $P_{\text{usr}}$ instantiates session-specific content: the session identifier, $\hat{p}$ and $m$, the line-numbered $E_0$ log block, and the E1–E5 evidence blocks. The structural constraints embedded in $P$ are designed to be directly enforceable by the Verifier described in Section 3.2.4.

The $E_0$ log lines are passed through the same dataset-specific normalizer used during evidence construction, replacing instance-specific identifiers — block IDs and IP addresses for HDFS; node identifiers, hexadecimal addresses, and numeric values for BGL — with typed placeholders. This ensures that $E_0$ and $E_1$–$E_5$ share a consistent lexical representation, allowing the LLM to focus on structural log patterns rather than incidental parameter differences. All log lines in $E_0$ and $E_1$–$E_5$ are prefixed with their span identifiers, and a header declares the total line count and valid span range for each evidence slot, bounding the line references the LLM may cite. For HDFS, the structural summary described in Section 3.2.1 is appended to $E_0$ so that the LLM observes the same operation-count tags present in the retrieved evidence. Each $E_1$–$E_5$ block additionally carries a metadata header that includes the evidence label (anomaly or normal). Exposing the label to the LLM is intentional: it enables the model to distinguish anomaly exemplars from the normal contrast session, which is necessary for generating correctly typed claims. This does not constitute label leakage because the labels belong to reference evidence sourced from the train split, not to the query session $E_0$ under analysis.

The prompt specifies a structured output format, referred to as the Trace Schema. The LLM must produce a structured explanation $T$ defined as:

$$T = (\hat{y},\ \textit{summary},\ \sigma,\ C)$$

where $\hat{y} \in \{\text{anomaly}, \text{normal}\}$ is the predicted label, $\textit{summary}$ is a concise forensic description with quantified observations, $\sigma = (\textit{name}, \{E_i\}_{\text{matched}})$ is the anomaly signature in COMPONENT\_\_ERROR\_TYPE format with matched evidence identifiers, and $C = \{c_1, c_2, c_3\}$ is a set of exactly three claims. An optional Boolean flag $\textit{ie}$ may be set when the provided evidence is genuinely insufficient. Each claim is a tuple:

$$c_k = (\tau_k,\ \textit{text}_k,\ \mathcal{E}_k,\ \mathcal{R}_k)$$

where $\tau_k \in \{\text{observation}, \text{pattern\_match}, \text{contrast}\}$ is the claim type, $\textit{text}_k$ is the claim text, $\mathcal{E}_k \subseteq \{E_0, \ldots, E_5\}$ is the set of referenced evidence identifiers, and $\mathcal{R}_k$ is a non-empty set of evidence spans in $E_i$-$L_j$ format. The prompt enforces a claim-type completeness constraint requiring exactly one claim of each type:

$$\{\tau_1, \tau_2, \tau_3\} = \{\text{observation},\ \text{pattern\_match},\ \text{contrast}\}$$

This constraint ensures that every explanation integrates direct observations from $E_0$, pattern matches against anomaly exemplars $E_1$–$E_4$, and behavioral contrasts with the normal session $E_5$.

The system prompt further specifies formatting constraints that render $T$ machine-verifiable. Each element in $\mathcal{R}_k$ must conform to either the single-line format $E_i$-$L_j$ or the range format $E_i$-$L_j$ to $E_i$-$L_k$; bare evidence identifiers, alternative separators, and placeholder line numbers are prohibited. Every claim must cite at least one span within the declared valid range, and the claim text must reference terms present in the cited lines to ensure span-level verifiability. For HDFS, the system prompt additionally provides a dataset-specific analysis procedure that distinguishes between sessions containing explicit error indicators and sessions whose anomaly is encoded in the operational sequence structure, reflecting the two empirically observed categories of HDFS anomalies. The assembled prompt pair $(P_{\text{sys}}, P_{\text{usr}})$ is submitted to the LLM with JSON-mode output enabled. The returned JSON response is parsed into the $T$ structure and forwarded to the Verifier for post-hoc schema and grounding validation.

#### 草稿正文

The Prompt Builder's structural constraints guide the LLM toward well-formed output, but prompt-time instructions alone cannot guarantee faithfulness: the model may fabricate evidence identifiers that do not exist in the provided context, cite log lines that contain no anomaly-related content, or produce span references that exceed the actual line count of an evidence slot. The Verifier addresses this gap through rule-based, post-hoc validation of each explanation $T$ against the evidence from which it was produced — without requiring a second LLM call or human inspection. Formally, the verification function is defined as:

$$V(T,\ E_0,\ \{E_1, \ldots, E_5\},\ \mathcal{M}) \to (b,\ \mathcal{F})$$

where $\mathcal{M}$ maps slot identifiers to evidence store IDs, $b \in \{\text{pass}, \text{fail}\}$ is the overall verdict, and $\mathcal{F} = \{f_1, \ldots, f_n\}$ is the set of individual check outcomes, each carrying a status $s_i \in \{\text{PASS}, \text{FAIL}, \text{WARNING}\}$. The overall verdict follows strict failure semantics:

$$b = \text{pass} \iff \forall\, f_i \in \mathcal{F},\ s_i \neq \text{FAIL}$$

WARNING outcomes are recorded as soft quality signals but do not block acceptance, preventing the pipeline from discarding explanations that are substantively correct but exhibit minor stylistic deviations.

The nine checks fall into three categories. *Structural checks* validate that the explanation conforms to the Trace Schema: required fields are present, every referenced evidence identifier belongs to the provided evidence set, the fraction of claims citing at least one evidence source meets a minimum coverage threshold, and the anomaly signature follows the canonical COMPONENT\_\_ERROR\_TYPE format. *Grounding checks* assess whether each claim is anchored in the evidence it cites, at two levels of granularity: first at the document level (claim keywords appear somewhere in the referenced evidence slot) and then at the span level (keywords appear specifically in the cited $E_i$-$L_j$ lines). The span-level check is the stronger of the two and is designed to catch claims that reference a correct evidence ID but point to irrelevant lines within it. *Severity checks* target the most common hallucination pattern observed empirically: the LLM cites normal INFO-level log lines as if they were error indicators. This check verifies that at least one cited $E_0$ line contains a genuine severity keyword (e.g., ERROR, WARN, FATAL, or dataset-specific exception terms); if none does, the explanation is flagged as a likely hallucination.

A key design consideration in the severity check is the *structural-anomaly bypass*. In certain HDFS sessions, the anomaly is encoded entirely in the operational sequence — missing pipeline stages or excess block replications — rather than in any explicit error message; every log line in such sessions is at INFO level. Applying the severity check naively would reject every explanation for these sessions as hallucinated, even when the explanation correctly identifies the structural deviation. The Verifier therefore first inspects whether the session contains any non-INFO severity lines; if it does not, the severity check is bypassed and the explanation is evaluated solely on structural and grounding criteria. This distinction between keyword-based and structure-based anomalies allows the Verifier to maintain high precision without sacrificing recall on anomaly types that lack explicit error indicators.

#### 草稿正文

Aggregating thousands of individual explanations into a coherent anomaly landscape requires a consistent labelling scheme. The Signature Generator assigns each explanation $T$ a standardized label in COMPONENT\_\_ERROR\_TYPE format (e.g., KERNEL\_\_DATA\_TLB\_ERROR, DATANODE\_\_BLOCK\_WRITE\_FAILURE), enabling deduplication, frequency counting, and cross-session pattern analysis. Rather than selecting from a fixed taxonomy, the LLM generates a raw signature name $\sigma_{\text{raw}}$ as part of its output, guided by dataset-specific component vocabularies and example names provided in the system prompt. A deterministic normalization step then maps the raw name to a canonical form:

$$\sigma(T) = \text{Normalize}(\sigma_{\text{raw}}(T))$$

This step is necessary because, without it, the same failure mode fragments into lexical variants that defeat exact-match aggregation — for example, the LLM may produce KERNEL\_\_FATAL\_\_DATA\_TLB\_ERROR (with an extraneous severity segment) or KERNEL\_\_FATAL\_\_data TLB error interrupt (verbose free-text) for what should canonically be KERNEL\_\_DATA\_TLB\_ERROR. The normalizer strips severity labels that the LLM inserts despite explicit instructions to omit them, consolidates variant phrasings to canonical error types, and corrects component prefixes. Signature format compliance is additionally enforced by the Verifier (Section 3.2.4) as a soft warning.

#### 草稿正文

The Reasoner pipeline described in Sections 3.2.1–3.2.5 invokes an LLM for every session flagged as anomalous by the Screener. In datasets with high anomaly rates this produces a proportional LLM cost, much of which may be redundant when many sessions share the same underlying failure mode. The Gating module sits between the Screener and the Reasoner and controls which anomalies receive LLM explanations under a given budget constraint. Let $N$ denote the number of sessions predicted as anomalous and $B \in (0, 1]$ a budget ratio specifying the fraction to explain. The gating function selects a subset $\mathcal{G} \subseteq \{x_1, \ldots, x_N\}$ with $|\mathcal{G}| = \lfloor B \cdot N \rfloor$:

$$\mathcal{G}(B) = \operatorname{top\text{-}K}\bigl(\{x_i\},\; u(x_i),\; K = \lfloor B \cdot N \rfloor\bigr)$$

where $u(x) = 1 - m(x)$ is the screener uncertainty and $m(x) = |p_{\text{anom}}(x) - p_{\text{norm}}(x)|$ is the classification margin. Sessions with low margin — those where the Screener is least certain — are prioritized for explanation, on the rationale that high-confidence anomalies are more likely to match well-understood failure patterns while borderline cases benefit most from detailed LLM analysis. When $B = 1$ the gating reduces to the explain-all baseline, which serves as the default operating mode and the reference point for cost-quality trade-off evaluation in Section~5.
