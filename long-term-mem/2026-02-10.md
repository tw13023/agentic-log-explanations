### 2. Built Data-Driven Discovery Pipeline (`notebooks/05_signature_audit.ipynb`) ✅

Implemented a 5-step fully automated approach:

#### Step 1: Automatic Token Discovery
- Extracted all words from anomaly and normal training sessions
- Computed discriminative score: `|anom_rate - norm_rate|` for each token
- Auto-selected tokens above 5% difference threshold
- Split into **anomaly-enriched** (present more in anomalies) and **normal-enriched** (present more in normals → structural absence signal)

#### Step 2: Fingerprinting
- Binary presence vector of all discovered tokens per session
- No hand-picked operations — uses only statistically discriminative tokens

#### Step 3: Clustering
- Grouped sessions with identical fingerprints into raw clusters

#### Step 4: Merging Overlapping Clusters
- **Key insight**: Many raw clusters differ only in normal-enriched tokens (e.g., one cluster has `delete` present, another doesn't — both have the same anomaly tokens)
- Merge key = anomaly-enriched tokens only → collapses structurally-similar clusters
- Also tracks which normal operations are **missing** per cluster (structural absence)

#### Step 5: Auto-Naming & Export
- Generated pattern names from dominant keywords (no hand-crafted if/elif mapping)
- Exported as Python dicts ready for `signature_generator.py`

## Key Design Decisions

1. **Threshold = 5%**: Any token with `|anom_rate - norm_rate| > 0.05` is considered discriminative. Catches both strong signals (fatal: 88% diff) and weaker but still meaningful ones (redundant: 5.7% diff).

2. **Merge by anomaly-enriched tokens only**: Normal-enriched tokens vary between clusters due to how far a session got before failing. Two sessions that both have `ioexception+writeblock` but differ in whether `received` is present are the same type of failure — just at different stages.

3. **Min frequency = 3**: Clusters with < 3 sessions are excluded from patterns (too rare to generalise). Covers 99.8% of both datasets.

4. **26 HDFS + 34 BGL patterns**: More fine-grained than the original 7+9. This is intentional — more specific signatures yield better RAG retrieval for the explanation pipeline.

## Session 2: Verifier Fixes, Permanent Pattern Storage & Pipeline Validation

### Objective
Integrate data-driven patterns into both pipelines, fix verifier bugs, achieve stable >90% verification pass rate, and create permanent pattern storage.

### Problems Found & Fixed

#### 1. Verifier Rejected Range Span Formats (`src/verifier.py`)
- **Symptom**: 5/17 HDFS sessions failed verification (70.6%), each with 7/8 checks passing
- **Root cause**: `_parse_span()` only accepted strict `E0-L12` format; rejected `E0-L6 to E0-L10` range format as "malformed"
- **Fix**: Enhanced `_parse_span()` to handle range formats: splits on `' to '`, `','`, and multi `-L` before parsing

#### 2. Verifier Rejected E0 as Evidence ID (`src/verifier.py`)
- **Symptom**: `evidence_spans_validity` check failed when LLM cited E0 spans
- **Root cause**: E0 (query session) wasn't in `evidence_id_mapping` — only E1-E5 were mapped
- **Fix**: Added `and eid != "E0"` condition in `_check_evidence_spans()` to accept E0 as valid

#### 3. `text_lines` UnboundLocalError (`src/prompt_builder.py`)
- **Symptom**: `UnboundLocalError: name 'text_lines'` in `format_evidence_block()`
- **Root cause**: `text_lines = hit.text.split("\n")` was used before being defined (variable ordering bug)
- **Fix**: Moved the assignment before its first use

#### 4. SignatureGenerator Keyword Matching Collapsed Patterns
- **Symptom**: 26 HDFS patterns collapsed to 1 when loaded via `SignatureGenerator`
- **Root cause**: First pattern's `ask` keyword matched everything, so all sessions got pattern #1
- **Decision**: Bypass `SignatureGenerator` entirely — load patterns directly from JSON as `EvidenceDoc` entries

### Clarified: Verification Passed vs Verification Checks
- **Verification passed** (session-level): A session passes when it has **zero FAIL** checks. This is the number that matters.
- **Verification checks** (individual-level): 8 checks × N sessions. WARNINGs (e.g., low keyword overlap) don't fail a session. Removed from batch summary to avoid confusion.

#### Features
- **YAML-based**: Human-readable and editable, version-controlled
- **Dependency tracking**: Tasks can declare `depends_on` — dashboard shows `⊘ blocked` for unmet deps
- **Pipeline integration**: `explain_all.py` auto-updates task status at start/complete/fail
- **Metrics recording**: Stores pass rate, token count, run time inline with task status
- **CLI dashboard**: `python -m tasks` shows progress bar, categories, inline metrics

#### CLI Commands
